## 5. Where Claude Code got it wrong and how we caught it
- 2026-10-18, feat/m6-drafts: the resume check caught a real gap. Killed a run with 8 drafters in flight and restarted at once: `run start` left the 8 jobs "still starting" (handed out under 3 minutes before), the Stop hook let the turn end, and the restarted `-p` run exited after 30 s with nothing done; a second restart after 3 minutes finished. Fixed in `run start` (no grace for an earlier session's jobs); re-run live: one restart, 8 drafts redone, run ended in 134 s, no other job repeated.
- 2026-10-18, feat/m6-drafts: four independent reviewer agents scored the 8 drafts of rehearsal run 2 against the briefs they were written from: 7 "ready with minor edits", 1 "needs work", about 7/10. Clean on style, numbers and names; the recurring fault was over-generalizing: a rule or role seen in one email written as standing (a 100 MW wheel limit from one Nov 2001 email; "Perry handles Planning requests"), the automation idea written as if it already existed ("check the meter-to-allocator list first"), report voice in owner lines, and forms missing fields their own text names. Fixed at the drafter instructions (single-email rules marked to confirm, new things as setup steps, a fixed owner line, a reread as tomorrow's user), not in the drafts, since the M8 run drafts again. Before/after (two more reviewers, same 8 processes re-drafted): about +1 point each (5-6 to 6-7); report voice, spelling and per-step roles fixed, but a forced "Currently: <name>" owner line made owner errors worse (one email about a spreadsheet became "settlement lead"; a one-day cover became the P&L owner while the person who wrote 33 of the emails was dropped), and invented controls persisted. Lesson: instructions alone gave diminishing returns; the fix moved the facts to code: the people line under each who-section is now written by code from counted participants and dated owner claims, the drafter proposes missing timings visibly as `[proposed: ...]`, and stalls become exceptions, not rules.
- 2026-10-16, main: First Windows fix (sparse checkout alone) failed because Git refuses to index trailing-dot paths on Windows at all. Caught by testing in a scratch clone before recommending it.
- 2026-10-16, main: In Git Bash, the sparse-checkout pattern `/corpus/` was silently rewritten to `C:/Program Files/Git/corpus/`; the exclusion did nothing and Windows wrote the corpus with stripped names (6,480 status changes). Caught by reading `.git/info/sparse-checkout`; fixed with `MSYS_NO_PATHCONV=1`.
- 2026-10-16, plan/architecture: The blueprint had the model estimate minutes per occurrence and the automation fraction, which would leave a model holding the key input to the hours arithmetic and let the headline move between runs. Caught in review; replaced with the email-trail model.
- 2026-10-16, plan/architecture: The revised blueprint treated a subject thread as one occurrence and any consecutive same-sender message as a chaser. The 18 "Calpine Daily Gas Nomination" emails share one subject and arrive days apart, so they would have collapsed into a few occurrences and been priced as chasers. Caught by grepping the real subjects and dates.
- 2026-10-16, plan/architecture: Static deny rules in the blueprint would have blocked our own development sessions; 90 KB batches sat too close to the Read cap. Both caught in review.
- 2026-10-16, docs/m-1-results: Running `claude -p "/m1test"` from Git Bash, the slash command arrived as `C:/Program Files/Git/m1test` (Git Bash path conversion), so the skill never triggered; the orchestrator recovered only by searching the disk for it. Caught in the experiment's stream log before any real run depended on it; the plan now requires `MSYS_NO_PATHCONV=1` for Git Bash, and the README will say so.
- 2026-10-16, feat/m1-reader: The reader decided "is this folder a Git checkout?" by comparing path strings. ## 7. Where the system is most likely wrong
- Which emails belong to which process is model judgment (cached). Measured against 52 labels (13 per mailbox, sampled by code). The main session drafted all 52 from the sample file alone, without seeing any extraction: exact process set 81%, any overlap 85%, role 81%. Scott, who is not an energy-trading specialist, then reviewed the 8 the labeller was least sure of, with recommendations made after the extractions had been seen: final exact 84.6% (44 of 52), overlap 86.5%, role 82.7%. The whole rise comes from two labels moved to the extractor's answer (an unsupported imbalance guess, an over-broad settlement tag), so the independent 81% is the conservative figure. Of the 8 process mismatches, 4 are the extractor proposing a `new:` key where a taxonomy key fit (`farmer-d/logistics/811.`, `giron-d/sent/327.`, `giron-d/sent/49.`, `williams-w3/sent_items/16.`), consistent with the 381 `new:` proposals the M5 synthesizer must merge; 4 of the 9 role mismatches are between personal, noise and automated.
- Occurrence counting is a heuristic, and it is the base of every dollar figure (occurrences per month x actions x minutes x $85). The corpus has no In-Reply-To or References headers, so threads are grouped by normalized subject (split after 45 days of silence) and a new occurrence starts at each fresh send. It can overcount (a new email with the same subject mid-conversation becomes a second occurrence) or undercount (a long back-and-forth is one occurrence, though its email actions are all still counted), and generic subjects ("meeting", "question") can group unrelated mail; only process-tagged messages count, which keeps personal mail out. To do in M5: spot-check the occurrences behind the top opportunities against the raw emails before trusting their numbers.
- The email trail is a floor: phone calls, spreadsheets and system entry leave no messages.
- 2026-10-18, feat/m5-timing: The model-made parts move between forced reruns, while a warm rerun repeats them exactly (they are cached). Two merger runs over the same extractions: 41 then 36 keys mapped to taxonomy keys, 35 then 40 promoted processes; with fresh estimates the A+B automatable headline went from $1,941 to $1,853 a month (about 5%), 60 then 65 processes. Counts and arithmetic do not move; membership and estimates do.
- 2026-10-17, feat/m5-score: The top 10 work estimates from the M5 live run were given to a separate reviewer subagent briefed as someone who knows 2000-2002 gas and power back offices (an AI check, not a human expert; Scott is not from the industry). It judged all ten minutes-per-round and automatable shares believable (none off by an order of magnitude; it would put credit-report automation higher and quarter-end audit requests' upper range higher). Its three cautions belong here: the round counts are what four mailboxes show, not how often the work happened (nominations, schedule checks and the credit report were daily or intraday jobs, mostly done by phone and screen), so every total is a floor; meter-flow coverage, imbalance reconciliation and nomination fixes are one logistics group's work and one underlying problem can surface in all three, so adding them can double-count part of a day; the automatable shares assume the deal, scheduling and ISO systems could be queried together, which in 2000-2002 they mostly could not.
- Forwarded reports whose headers were stripped carry no marker, so their whole text counts as the sender's own and they are priced as long written emails (15 min, 30% automatable) instead of forwards (2 min, 80%). 13 messages: `williams-w3/inbox/23, 35, 49, 57, 62, 75, 86, 92`, `farmer-d/logistics/25`, `giron-d/inbox/127, 180, 468`, `lokay-m/sent_items/147`. The parser subagent found the shape; the code review counted all 13.
- De-duplication ignores recipients, as specified: 5 of the 39 merged copies went to different people (e.g. two all-staff lists 21 minutes apart, `giron-d/inbox/434.`/`435.`), so the dropped copy's reads are not counted. Each is marked `recipients_differ` in `out/dedup.json`.
- An address written as `jdoe@enron.com (Doe, John)` loses its display name: the comma inside the parentheses splits the list. The address itself is kept, so counts are unaffected; only a shown name is missing.
- The batch token estimate, (bytes + 8 x lines) / 3, is calibrated for this all-ASCII corpus; CJK or base64-like text could tokenize denser than estimated and exceed Read's real 25,000-token cap. Unmeasured.
- The injection scanner is phrase-based and tuned on the one planted example; a trap worded differently ("note to the LLM") would pass it. The extractor prompt is the second line of defence.

## Artifact choices (the brief: "you defend that decision in your notes")
- 2026-10-18, feat/m6-drafts: **What we draft and for which opportunities.** One artifact per opportunity in tier A or B, the top 8 by automatable dollars (at least 3), of the type the synthesizer chose for the process (SOP, checklist, email template, template); a process whose synthesis says no artifact helps gets none and its slot is not passed down. Each is the process team's own working document, written to be used the next morning; code adds the title, a provenance line and the verbatim evidence. Decisions: `.claude/notes/DECISIONS.md` (2026-10-18 entries).
- 2026-10-18 (Scott and Claude): **Reusable email templates, not one-off emails about in-flight threads.** The brief lists "a draft email" as an example. We draft a ready-to-send email for the recurring situation (subject, recipients by role and name, full text, blanks only for the details that change each time, when to send, what to do if nobody replies). Why: (1) the brief is about recurring work, and a reusable email cuts time on every future occurrence where a one-off email saves it once; (2) a one-off email about a specific open item needs that item's exact meter, volumes and dates, where a drafter is most likely to get a detail wrong; (3) the archive ends in 2002, so a thread that looks open may have been settled by phone, and a "send this tomorrow" chase would present a stale snapshot as current. In-flight work is shown instead on the dashboard (M7) as counted, cited "open loops" per process. Possible later addition: one worked example per template, filled only with values quoted in the latest real case.
