# Decisions

One line per non-obvious choice: what we chose, what we rejected, why. Newest last within each group.

## Setup
- **Develop natively on Windows; keep the corpus in Git objects, off disk** (per-repo `core.protectNTFS false` + sparse checkout excluding `/corpus/`). Rejected: WSL or Docker (works, but doesn't make the deliverable portable); full checkout with `protectNTFS false` (Windows writes `1.` as `1`, Git shows 6,480 changes, a commit would rename the corpus); renaming the corpus (citations would stop matching the reviewer's files).
- **A message's identity is its exact Git path, trailing dot included** (`corpus/farmer-d/logistics/1.`). The reviewer checks citations against raw files, so the ID must be the name they see.
- **One corpus reader with two sources (disk, or `git cat-file --batch`), byte-identical by test.** Rejected: a renamed on-disk mirror as source of truth (Windows and macOS/Linux would cite different names).
- **`corpus-view/` (`1.` -> `1.eml`) is git-ignored and for humans only.** Browsing on Windows without it ever becoming a citation source.
- **`.gitattributes`: `corpus/** -text`.** 3,231 of 3,240 messages contain CRLF (mostly in headers; most bodies are LF) and Git for Windows defaults to `core.autocrlf=true`; pinned bytes keep hashes and quotes identical across OSes.
- **Prove portability with a CI matrix (Ubuntu, macOS, Windows)** on the model-free tests rather than owning Mac/Linux machines.

## Architecture
- (Superseded 2026-10-17, see the next entry.) **Headline hours come from the email trail, not model estimates.** Code counts actions per occurrence (written, read, forwarded, chased) x fixed published minutes and automatable shares x $85/h. Rejected: model-estimated minutes and automation fraction (a model would hold the key input to the hours arithmetic the brief says it checks; the headline would move between reruns; planted effort claims like `482.` could push it). Cost: a floor that misses off-email work; the model's off-email estimate is shown beside each opportunity, never added in.
- **Hours = counted occurrences per month x estimated work minutes per occurrence + counted email time (decided 2026-10-17, before M5).** Run on the M4 outputs, the email-only method gave about $400/month automatable for the whole archive and $68/month for the top process: it priced the email about the work, not the work, which is what the brief asks about ("where that company is losing time", "the work that happens over and over"). The work minutes and their automatable share are a model's estimate per process, from cited evidence, bounded and checked by code, never set by one person's claim, cached and overridable from a file; counts and all arithmetic stay code. Rejected: email time only (measures the wrong thing); one flat published work time for every process (deterministic but treats an expense report like a month-end close).
- **An occurrence starts at each fresh send (no `re:`/`fw:`, no quoted text); a chaser must be a follow-up.** Rejected: occurrence = subject thread with 45-day split. The 18 "Calpine Daily Gas Nomination" emails would have collapsed into a few occurrences (tier C, out of the headline) and every daily send would have been priced as a chaser.
- **Only company staff time is priced (`priced_domains`, default `enron.com`).** Rejected: price every sender and recipient. $85/h is the blended cost of the company's staff; counterparty actions are counted and shown, not priced.
- **A message tagged with several processes splits its priced minutes evenly between them; occurrences and tiers still count it under each.** Rejected: full minutes under every process (the opportunities would add up to more time than was spent; 14 of 2,345 tagged messages carry two processes) and one process per message (drops real information). Raised by Scott while reviewing the gold labels.
- **TypeScript on Node >= 22.18, zero runtime deps.** Rejected: Python 3.11 stdlib (better built-in email and date parsing). Hooks need one interpreter name on every OS (`node`; Python is `python3` on macOS, `python` on Windows), one language spans pipeline, hooks and dashboard, and Scott reads TypeScript daily. Install burden was not a factor. Consequence: strict hand-rolled date parser, never `new Date(string)`.
- **Extractor subagents on `sonnet` at medium effort, drafters on `sonnet`, the synthesizer on `inherit` (the session model).** Rejected: the session model everywhere. Extraction is tagging and quoting across ~75 calls and the quote validator catches errors. Revisit if M3 shows poor tagging.
- **Artifact threshold: tier A/B, top 8 by automatable $/mo, at least 3; dollar bar set after the first full run.** Rejected: fixing $1,000/mo now, blind to the real distribution.
- **Dollar scope: observed in 4 mailboxes, labelled.** Rejected: extrapolating to the company (an invented number). Logged as next-week work.
- **Commit model outputs (extractions, taxonomy, synthesis); not batch files.** The brief requires one real run's output and no repeated work; README explains the warm rerun and `--force`.
- **Injection message shown as a flagged finding with citation**, not handled silently.
- **Taxonomy generated once by the model, cached, reviewed by us, never hand-edited.** Rejected: a hand-written list (we would be doing the identifying the brief asks the system to do).
- **Personal/noise mail classified, excluded from processes, counted on the dashboard.**
- **Headline total = tiers A+B; "including low-confidence" beside it.** Tiers depend only on occurrences and participants.
- **Orchestration: `/observe` skill fans out subagents from a code-kept queue.** Rejected unless forced: a script spawning `claude -p` workers (weakens "runs inside Claude Code"). M-1 tests the mechanics before any pipeline code; M3 is the go/no-go gate on real batches.
- **Corpus guard enforced only during pipeline runs or inside pipeline subagents.** Rejected: static deny rules (they also block development sessions from `corpus-view/` and feature-branch pushes).
- **Batches capped at 64,000 bytes and 22,000 estimated tokens, tokens estimated as (bytes + 8 x lines) / 3 to cover the line numbers Read adds.** Measured: 99 batches. Rejected: 90 KB (too close to the Read tool's 25,000-token cap on number-heavy text).
- **Trap detection is content-based only**, never keyed to the 16-digit Message-ID shape that identifies the planted messages.
- **Tagging accuracy measured against ~50 hand-confirmed labels.** Turns "where the system is most likely wrong" into a number.
- **Dashboard and report get a design pass Scott signs off before M7 is built.** The audience is a client president; plumbing alone doesn't meet the brief.
- **Cut line agreed in advance** (re-score CLI, off-email estimate, macOS CI, debugging skill); never cut coverage, quote validation, traps, drill-through, timing.

- **Keep the agent-loop orchestration (M-1 passed); the Stop gate uses the payload's `background_tasks`.** Rejected: the `claude -p` worker-pool fallback, no longer needed. Git Bash users prefix `MSYS_NO_PATHCONV=1` so `/observe` isn't rewritten into a path.

## Orchestration (M4)
- **The SubagentStop gate only records; fix rounds are re-dispatches driven by the orchestrator.** `status --json` lists what to dispatch next (retryable failures first), and `dispatch` on a failed batch prints a fix prompt with the previous output and its problems, up to 4 dispatches per cache key. Rejected: keeping in-agent blocking under `-p` as an optimisation (two behaviours, so the timed run wouldn't measure what a reviewer in auto mode gets) and resuming subagents by message (bypasses the concurrency limit, never exercised).
- **Taxonomy: a deterministic digest, one `taxonomist` subagent on `inherit`, acceptance by code.** The digest is four bounded views of the corpus (subject words, recurring subjects, a stratified sample of own-text snippets, top senders), not subject clusters: 2,422 distinct normalised subjects meant the 80 largest clusters covered 11% of mail. `taxonomy accept` validates the proposal (8-30 processes, slug keys, example subjects that really exist) before it enters any cache key. Rejected: a lighter model for the taxonomist (one cached call whose error costs a full re-extraction); a hand-written list (we would be doing the system's identifying). Model choice awaits Scott's approval.
- **Each extractor is bound to its batch on its first batch read**, and the guard denies writes to any other batch's output; the gate uses the binding, so nothing parses model text for control. Rejected: trusting an `OUTPUT:` line in the model's reply.
- **Committed ledger files make a fresh clone's first run warm.** Done means the ledger says done, the recomputed cache key matches, and the validated file carries the batch's `content_sha`; `node obs.mjs verify` re-checks every done batch against the corpus. Rejected: re-validating every batch on every run.
- **A Stop hook keeps the orchestrator from quitting with work pending**, blocking with the exact next command and never twice for the same reason; `run start` stamps batches left `running` by a crash or a usage-limit pause, so resuming is rerunning `/observe`.
- **Fix rounds pass problems through a file, not through the orchestrator.** The problem list is written to `out/fix/<batch>.txt` when the failure is stamped, and only that batch's extractor may read it; the orchestrator sees a short fixed prompt, and `validate` prints counts plus at most 3 bounded, escaped problem lines. Rejected: printing problem lines (with email-derived quote previews) into the orchestrator's conversation and the next agent's prompt.
- **A running batch counts as abandoned only after a grace window (3 min) with no live extractor, or after 15 min regardless.** Rejected: trusting the background-task registry alone, which on an empty or unfamiliar reading would have failed every live batch at once.
- **The taxonomy gate rejects catch-alls, instruction-like text and one-off processes, and caps the file at 24 KB.** Rejected: checking only key format and that example subjects exist, which admitted a steered taxonomy in review.
- **Only passing extractions are kept in `out/validated/`; scoring and rollup read done batches only.** Rejected: keeping a failed batch's validated file, which accuracy scoring would have counted.
- **A circuit breaker:** a missing-output failure costs a dispatch only on its second occurrence for that batch, and the run halts with a reason if 6 batches lose their output within 10 minutes (e.g. a rate limit), instead of burning every batch's retries.
- **Gold set after the taxonomy:** 52 messages sampled by code (13 per mailbox), labels proposed by the main session without opening any extraction, confirmed by Scott, scored by code against the taxonomy they were made for.

- **Scott's morning review, 2026-10-17:** the 25-process taxonomy from the first live run is approved as is (Scott deferred the domain judgement to Claude: the list matches the operational mail seen); the taxonomist stays on `inherit`; the gold set is checked by a person on the labeller's least-certain entries (option A) rather than all 52; extraction concurrency goes up from 12 to the platform's default ceiling of 20 to keep the cold run well inside 30 minutes.
- **M5 design approved by Scott, 2026-10-17 (ARCHITECTURE.md 6.19-6.21, 14):** merge the extractors' `new:` keys before counting, with one `merger` subagent on `inherit` and promotion sized by code (>= 3 messages, 3 rounds, 2 subjects, 2 months; smaller stays an unpriced lead); work estimates bounded by code (1-480 min per round, automatable <= 80%, quotes from >= 3 rounds by >= 2 senders, so one person's claim can never set a value); a round seen only through an email shared with another process counts as half; tiers from counts only (A >= 40 rounds, 6 months, 3 staff; B >= 10, 3, 2; C outside the headline), which on the M4 keys gives 14/9/2 instead of 23 A; `config/estimates.json` overrides by default, labelled. Rejected: the plan's original tiers (did not discriminate) and promoting on the model's say-so.
- **M5 built sequentially in two sections, one implementer each, not five in parallel.** Scott: separate agents building against a spec produce disjointed work; there is no rush on implementation. Section 1 is the deterministic numbers, section 2 the Claude Code layer and the live run, each reviewed once.
- **A one-call `refill` command for the orchestrator.** M4's run log showed about 6-7 of 12 extractor slots busy on average, because each refill took several orchestrator turns (status, validate, dispatch per ID, then the Agent calls). Rejected: relying on the 20-slot cap alone (more slots refilled in the same waves).
- **Only the session that ran `run start` owns the run.** The guard records the session on that command; the first pipeline spawn is a fallback only when nothing is recorded. Rejected: the first build's "latest spawner wins", which review showed let a second window (e.g. `/extract-batch`) take the run over and silence the real orchestrator's Stop hook.
- **One agent per job dispatch.** The first agent to bind a job at a dispatch count holds it; a second is refused for every job kind. Rejected: M4's first-come binding per agent, under which two agents could write one job.
- **A refused or failed Agent call is reported at once (`refill --failed <id>`)**, stamped like an orphan with no output. Rejected: waiting out the 3-minute grace window, which could end an unattended run early when it was the last job.
- **A process whose quotes cannot meet the evidence rule gets no estimate and is priced on its email alone;** the evidence sample adds up to two quotes so that at least 3 senders show when the process has them (25 of 25 processes can meet the rule on the M4 data). Rejected: requiring an estimate for every process, which would have exhausted a group on a process with one sender in its quotes.
- **Ownership conflicts count only claims that resolve to a person:** against the whole people directory (process participants preferred on ties), or a one-to-three-word name with no group word; group claims ("each trader") never count, and spelling variants of one person count once. On the M4 data 6 of 25 processes show a conflict, the planted `483.`/`526.` pair included. Rejected: matching only the process's participants (dropped real people named in bodies, so a reviewer-added trap could be missed).
- **Proposed keys capped at 60 characters in extraction validation**, without editing the extractor prompt (that would re-key all 99 committed batches); the longest committed key is 45.
- **The merger runs at `effort: medium` and writes a compact proposal (Scott approved, 2026-10-17).** The M5 live run's merger took 11 min 39 s, one call writing a 49 KB pretty-printed proposal, which a 30-minute cold run cannot afford. Its proposal now lists keys under `mapped` (by taxonomy key), `unassigned`, and promoted processes with only key, name, definition and aliases (nothing downstream read the include/exclude notes); the same decisions re-encode to 23 KB. Validation is as strict as before, plus a check that no key appears twice in one JSON object (a repeated taxonomy key would otherwise silently drop its first list). Rejected for now: splitting the merge across parallel agents (aliasing across the whole list is the point; revisit only if the re-measured merger is still over about 4 minutes); lowering the taxonomist's effort (held unless the timed run needs it).
- **The merger maps more readily:** a step, check, report, correction, variant or follow-up of a taxonomy key's work is that key, read broadly; promotion only for work no key covers even then. In the live run all 4 gold cases where an extractor proposed a new key although a taxonomy key fit ended up promoted, none mapped. The wording is generic and draws nothing from the gold labels, which measure the result.
- **On merged keys, a gold `new:*` label agrees with any extracted key outside the taxonomy** (promoted or unassigned): the labels predate the merge and cannot name a promoted process. The first scoring rule showed 75.0% exact for the live run, an artefact; the corrected rule gives 84.6%, the same as unmerged.
- **Getting the cold run under 30 minutes (Scott, 2026-10-18).** The first cold run took 32 min 34 s before drafting existed. An independent analysis of its logs found the bottleneck was not the extractors (p50 91 s each at 20 in flight vs 85 s at 12, no throttling) but the orchestrator typing every Agent prompt (~776 characters of paths, ~3.5 s per call, agents start only when the whole message is written), so slots sat empty in waves (10.0 of 20 busy on average). Chosen: job prompts that carry only the job ID (agents derive their own paths); one command per cycle for every ready deterministic step; synthesis in one balanced wave; fewer avoidable fix rounds; timestamped stage events in the run log; projected ~26.5 min with drafting. Rejected: a faster model for the orchestrator via skill frontmatter (the docs say it lapses after the turn), two batches per job (~0.3 min once prompts are short), 16 in flight (slower). In reserve: extractor `effort: low`, only after a gold-set check.
- **Every pipeline agent pins its model and effort (Scott, 2026-10-18):** taxonomist, merger and synthesizer `opus` at `medium`; extractor and drafter `sonnet` at `medium`; the orchestrator stays on the session model (it makes no judgement). Rejected: `inherit`, under which the user's own settings changed both timing and output (the development session's `effortLevel` (`xhigh`) reached every `inherit` agent; a reviewer on defaults or a smaller session model would get different process lists, merges and estimates).
- **The submitted outputs come from one fresh cold run in the real repo at M8 (Scott, 2026-10-18)**, timed, its logs committed with it. Rejected: the current composite (M4 extraction, later merge and synthesis runs, timing proven separately in a clone), which is not "one real run" and goes stale once the agent files change. Cost: Scott re-approves the new process list and the gold set is relabelled blind against it.
- **Section 15's open details, decided by the main session under Scott's delegation (2026-10-18):** the job prompt keeps a `Project folder:` line permanently (nothing rests on a subagent knowing its working directory); the ownership `mentions` check is relaxed to word level, matching the rollup's own name matcher, and the extractor wording is tightened (4 of 5 extraction fix rounds were this check); a draft gets at most 2 dispatches (a failed draft leaves its opportunity without an artifact, never a failed run); drafting briefs are committed (their quotes are already in the committed validated files); an opportunity whose synthesis says `artifact_type: none` gets no artifact and its slot is not passed down the ranking (we draft only where an artifact helps); synthesis groups hold up to 4 processes so they fit one wave.
- **Drafted artifacts read as professional business writing, checked by code (Scott, 2026-10-18):** the drafter is told to write plain, direct prose with no em dashes and no stock AI phrasing, and the draft gate rejects an em dash, a spaced en dash or ` -- `, and a short list of unambiguous AI-tell phrases in the drafter's body (one constant feeds both), so the fix round repairs it. Rejected: instructions alone (not enforced) and rewriting the text in code (silently changes the draft). Ordinary business words (`streamline`, `comprehensive`) are not on the list, and the code-rendered evidence quotes are exempt.
- **Each artifact type has headings that fit its reader (Scott, 2026-10-18):** an artifact is the process team's own working document, usable the next morning, not a report about them. SOP: Purpose, Owner, When to run, What you need, Procedure, Exceptions and escalation; checklist: Purpose, Owner, When to use, Before you start, Checklist, If something is off; email template: When to send, Sender and recipients, Email, If there is no reply; template: Purpose, Who fills it in, When, Template, Where it goes. One constant feeds the drafter and the gate. Rejected: one fixed list of six (Owner, Trigger, Inputs, Steps, Outputs, Exceptions) for every type, which made an email template read as a specification with the email inside it.
- **The draft gate checks for planted instructions, not for imperative prose (2026-10-18, after the M6 review):** an SOP is made of orders, so the extraction-time steering patterns ("do not report", "the reviewer must", "ignore the old tab", "System:") would have failed ordinary drafts with one fix round to spare. Drafts are checked only for text aimed at the pipeline (injection markers; AI, model or automated-reader addressees; "ignore previous instructions"; "mark this as automated"), and every problem line quotes the sentence. Effort numbers: hours and minutes are allowed as deadlines or frequencies ("within 24 hours", "every 2 hours"), not as effort ("takes 2 hours"); dollars and percent never; the same for numbers in words. Counts of rounds, emails or people are left to the drafter instruction, not gated, because "check 3 times a day" is a real schedule. Rejected: reusing the extraction steering set unchanged.
- **A restart picks up the jobs an interrupted run left at once (2026-10-18, found by the resume check):** `run start` stamps every running job without the 3-minute grace, since its session has replaced the earlier one and no earlier agent is alive; the grace stays for jobs a live run has just handed out. Live: killed with 8 drafters in flight, restarted at once, all 8 redone and the run ended in 134 s, nothing else repeated. Rejected: keeping the grace at run start (an immediate `-p` restart ended in 30 s with nothing done). Cost accepted: two sessions on one folder at the same moment can hand one job out twice; the later result supersedes.
- **Code writes the people line in every artifact (Scott, 2026-10-18):** under the who-section heading, code states who the emails show doing the work (counted) and who was named as owner (dated); the drafter writes the role and duties only. Rejected: a drafter-written "Currently: <name>" line, which promoted whoever appeared in one email to owner. Missing timings are proposed visibly (`[proposed: same day]`) rather than invented or left blank; stalls become exceptions, not rules.
- **Email artifacts are reusable templates for the recurring situation, not one-off emails about threads still open in the archive (Scott, 2026-10-18):** recurring work gets a reusable fix that saves time on every occurrence; a one-off email would need instance details a drafter is most likely to get wrong and would present a 2002 snapshot as current. Open items go on the dashboard as counted, cited open loops (M7). Must be defended in NOTES.md (NOTES-LOG "Artifact choices").
- **After the first cold rehearsal with drafting (29:51, Scott, 2026-10-18):** (1) the catch-all word rule stays as strict as it is (a bucket such as `business-matters` would be priced on the dashboard as if it were work); the merger instead gets the example the taxonomist already has (`business-travel-arrangement`: name the work, `travel-arrangement`), since its one breach cost a 1:45 fix round. Rejected: allowing `business` as a first word. (2) The draft gate still rejects an amount of hours or minutes by default, but a bare unit ("an hour", "each hour", "hour ending 7") is not an amount, and an amount used as a schedule, deadline, wait or frequency passes ("within about 24 hours", "every 2 hours", "24 hours notice", "the 16 on-peak hours"), because this company schedules power by the hour. Rejected after review: passing hours unless an effort word stood next to them, which let ranges ("allow 1-2 hours"), labels ("Estimated time: 2 hours") and many other phrasings through; a borderline sentence that is rejected costs one fix round whose problem line quotes it. How long the work takes stays the footer's checked estimate only. (3) The `/observe` skill pins the orchestrator's effort at `medium` (frontmatter `effort`), its model stays the session's: it runs commands and copies their output, and a run should not depend on the user's own effort setting. Measured per-cycle cost: about 30 s from a completion to `advance` and about 1.2 s per Agent call written; `advance` itself runs in 0.4 s. Rejected: more than 20 subagents in flight (slots were 58% busy) and extractor effort `low` (held in reserve, needs a gold-set check).
- **Gold set confirmed, 2026-10-17:** Scott read plain-English summaries of the 8 entries the labeller was least sure of and accepted the recommended label for each (4 changed); the other 44 stand as drafted. The 8 recommendations were made after the extractions had been seen, so NOTES reports the independent draft's score beside the final one.

## Build
- **TypeScript 7.0.2 and `@types/node` 22.20.5, pinned, as the only dev dependencies; no runtime dependencies.** Node types match the oldest supported Node (22.18) so the typecheck rejects APIs that Node lacks. Rejected: `@types/node` 24 (would accept APIs missing on 22).
- **All text files use LF on every OS (`* text=auto eol=lf`); the corpus keeps its raw bytes (`-text -eol`).** Rejected: platform-default line endings, which would make golden outputs and hashes differ on Windows.
- **CI also runs on Node 22.18.0**, so the `engines` claim is tested rather than asserted.
- **CLAUDE.md's greppable rules are tests (`tests/source-guards.test.ts`)**, proven by planting violations that each guard caught.
- **The message list comes from Git HEAD; a disk walk (skipping hidden files like `.DS_Store`) only when there is no Git checkout**, e.g. a ZIP download on macOS. Bytes are read from disk when every listed file is there, from Git objects when none are, and a partial checkout is refused rather than half-read. Rejected: walking the disk always (picks up stray files, and can't see the corpus on Windows).
- **Dates are parsed strictly: three-letter weekday and month names, a numeric offset, real calendar days, UTC by integer arithmetic.** Valid dates outside 1998-2002 are `out_of_range`, never guessed (year 0001 is not silently read as 2001). Rejected: lenient parsing, which would accept `Tues` and `Febuary` and roll impossible days forward.
- **Quoted and forwarded text is found by markers measured in this corpus**, including Lotus reply header blocks with no banner (the third most common, 477 messages). The injection scan reads subject plus whole body, quoted parts included, and undoes leftover `=20`-style encoding only for detection; offsets never change. Oversize = body over 32,000 characters (flags only the 350 KB table). Rejected: treating underscore rules as separators (in this corpus they are table lines).
- **One subject-prefix grammar shared by parsing and action counting** (`re:`/`fw:`/`fwd:`, any case, optional spaces, optional opening bracket as in `[Fwd: ...]`). Rejected: a strict `^fwd?:` in the classifier, which would have called `[Fwd: x]` fresh in one place and a forward in the other.
- **A chaser must go back to at least one of the same recipients.** Rejected: same sender as the previous message is enough (the plan's first wording), which priced one person forwarding an item to different colleagues in turn as nagging (about 95 such cases in the corpus, found by the code review).
- **The injection scanner has 9 named phrase patterns**: the 5 from section 6.3 plus 4 generic ones (ignore previous instructions, system prompt, language model, addressed to an AI). It flags exactly the one planted message; phrases common in business mail ("disregard previous instructions", "do not cite") were left out to avoid false positives. It is a first line of defence: the extractor prompt treats every message as data regardless.
- **A "forward" must actually forward something (its first earlier block is a forward banner, or an `FW:`-style subject) with a short note.** A short reply that only quotes the original is a short written email. Rejected: the plan's first wording ("any forwarded/original marker"), which would price every quick "Thanks" reply as an 80%-automatable forward.
- **Duplicate clusters are anchored on their earliest copy, strictly under 24 hours; exactly 24 hours apart is two emails.** Rejected: chaining each copy to the previous one (the first implementation), which collapsed a run of daily sends spaced a little under 24 hours into one email.
- **An undated copy counts as a duplicate only when its dated copies form one cluster; with no dated copies at all, nothing merges by content.** The canonical is the lowest-ID dated copy, so a date is never dropped for an undated copy. Rejected: matching an undated copy to any same-content message, which could chain separate daily sends together through it.
- **Each duplicate records how it joined and whether its recipients differ.** `rule` is `content` only for a copy in the canonical's own 24-hour content cluster, otherwise `message_id`. Rejected: one label per group, which hid mixed groups from anyone checking by hand.
- **Thread IDs come from a hash of the thread's first message ID (12 hex characters, and a collision stops the run)**, so adding or removing other threads never renames a thread or changes unrelated batch content. Rejected: sequential IDs; 8 hex characters (about a 0.08% collision chance on this corpus).
- **Every (message, process) tag needs its own verbatim quote that passes validation, or the tag is dropped.** Every message counted toward a process can then be traced to text in the raw email, which is what the brief's random spot checks test. Rejected: quotes only for a sample of messages per process, which would leave most counted messages unprovable.
- **Pipeline subagents run under an allowlist, not a deny-list.** An extractor may only Read inside `out/batches/`, `out/taxonomy.json` and `out/extract/`, and only Write `out/extract/batch-NNN.json`; every other tool and path is denied by the PreToolUse hook. Rejected: denying paths that mention the corpus (the first build), which let an extractor write over the guard hook itself, the ledger or validated results, and let Glob/Grep patterns walk around it. With a planted injection in the corpus, that was a real path to steering the system.
- **Extractor `maxTurns: 16`.** First pass plus three fix rounds needs about 12 turns; 16 leaves slack for a second Read or a retried Write. A tuning value, not a model or counting change.
- **Model output problems block only for claims; environment failures never go back to the model.** A rejected extra quote is recorded and never ships but doesn't cost a fix round when its tag already has an accepted quote; `setup:` problems (missing files, changed bytes) are logged and left for `node obs.mjs validate` instead of being handed to a model that can't fix them.
- **The M3 spike runs batch-000 and batch-074** (the batch holding the planted injection), so the go/no-go also tests whether the extractor reports the injection rather than obeying it.
- **The run ledger is one state file per batch, not one shared file.** Up to 12 extractor hooks finish at once; separate files have a single writer each, so no update can be lost. A batch counts as done only if its validated output exists and its cache key (batch content, extractor definition, taxonomy) still matches.
- **Batch rendering is bounded and fails loudly.** Header values are flattened to one line (no CR/LF or Unicode line separators, so a planted subject can't fake a new message), body tags are 16 hex characters (8 could be brute-forced by a determined author), shown header values are capped (500 characters per value, 600 addresses per list, 20,000 bytes of header lines per message; real maximums are 143, 594 and 14,634, so nothing real changes), every shown body is capped at 1,200 lines and 32,000 bytes (about 1.6x the longest real email, 753 lines; only the 350 KB table is cut) with a stated omission marker, and a batch over its byte, token or 2,000-line cap stops the run with a one-line `BatchError` rather than writing a file a subagent can't read whole. Rejected: silently truncating batches.
- **Batch files carry no taxonomy; the extractor reads it separately.** Rejected: the plan's first layout (taxonomy at the top of every batch), which would invalidate every cached extraction whenever only the taxonomy changed.
- **Body markers are tagged with a hash of the message's own Git blob ID**, so an email cannot fake the end of its body or the start of another message. Rejected: fixed `[BODY]` markers, which a planted email could imitate.
- **The deterministic stages always rerun (`prepare`, no model calls) instead of caching**; their outputs are byte-identical on unchanged input, so model-stage caches keyed on them stay valid. `parse`, `normalize` and `batch` were folded into one `prepare` command.
